## 强制规则

### 架构红线（每项目填写，置于最前）
- <示例：前后端所有通信走 P2P 通道，禁止新增 HTTP/WebSocket 直连端点和新监听端口。>
- 新增任何网络端点、端口监听、外部连接、存储访问时，必须在交付说明中显式指出，并对照本节红线自查。
- 涉及网络/端口/跨服务的功能，localhost 单进程跑通不算验证，必须用 docker-compose 等模拟部署拓扑后再验证。

### 依赖与实现
- 新增依赖前按顺序检查：标准库 → 已安装依赖 → 框架原生，都不行才新增，并说明理由。
- 数据库访问只用 ORM；i18n 只用 i18n 库；日期、校验、认证等见 docs/TECH_STACK.md。禁止自研这些能力。

### 复用优先
- 写任何新函数/组件前，先在代码库中 grep 相似实现。有则复用或扩展，禁止平行重写。
- 公共代码只放：<本项目填 utils/ components/ services/ 路径>。

### Git
- 构建不过不提交：提交前必须通过构建/编译 + lint；没验证能构建的代码禁止提交，构建环境跑不了要说明。
- 禁止 git add . 或 git add -A；逐文件添加，提交前 git diff --staged 自查。
- 不得提交 .db/.sqlite/.env/日志/构建产物/模型文件。

### 文件位置
- 测试统一放：<本项目填 tests/ 或与源文件同目录>。
- 文档统一放 docs/ 对应子目录；一次性笔记放 docs/notes/；临时脚本放 tmp/。

### 测试
- 只运行与当前改动相关的测试；全量回归需用户明确要求。
- 单用例 60s 超时；禁止依赖真实外部服务和 sleep；优先写最小验证而不是大测试。

### 大任务门禁
- 涉及多租户改造、数据迁移、换框架、跨模块重构等大改动时：先停在方案阶段，产出影响评估（涉及文件、迁移方案、回滚方式、分阶段计划）等用户确认，不得直接改代码。
- 接到大需求先回答"是否有更小的实现路径"，给不出也要说明代价。
- 单次改动超过 10 个文件或涉及表结构变更时，主动建议拆分成多个阶段。

### 代码移植
- 移植其他项目的代码时按阶梯就低选择：能直接依赖不复制；多项目复用建议抽库（submodule/私有包）；单处使用则原样复制 + 外层薄适配；重构移植需先出影响评估等审批。
- 移植是搬运不是重写：diff 只允许 import/路径、基础设施接入、逐条说明的必要修改；禁止顺手重构和加抽象层。
- 移植入库时标注来源项目与 commit hash。
- 发现同一段代码要出现在第二个项目时，先建议抽库而不是复制。

### 重构纪律
- 功能任务中不做任何任务范围外的重命名、移动、格式重组；发现坏味道只记录在交付说明的"发现但未改"清单，不动手。
- 重构必须命中触发条件（挡住需求 / 重复代码第二份 / 同处反复出 bug），否则不做；"更优雅"不是理由。
- 动手前先读 docs/design/adr/ 中相关决策，已决策事项不得重新发明；要推翻已有 ADR，先说明其结论为何失效并等确认。
- 同一段代码 30 天内已改过两次再要改时，先停下来建议补一条 ADR 由人拍板。

### 环境配置
- 本项目配置格式统一为 <yaml/toml/json/env 四选一>，禁止混用，禁止引入第二种格式；配置文件在 <路径>。
- 新增配置项只加在基础配置（含默认值，不加配置也能启动）；环境文件只放差异覆盖，禁止为环境单独维护全量配置。
- 环境变量只用于密钥，且必须同步登记 .env.example；禁止把非密钥明文值改成环境变量引用——确需如此，先说明并等确认部署侧已配置。
- 脱敏只作用于集中定义的密钥清单；非密钥配置和排障/临时日志不打码。要看真实值：本地临时打印（不提交）或 debug 开关，不是永久脱敏。
- 配置改动必须随功能 PR 提交，并在交付说明中列出改动清单；改了不提交等于功能未完成。
