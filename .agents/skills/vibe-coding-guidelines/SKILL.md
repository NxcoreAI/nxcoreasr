# AI 辅助开发规范（Vibe Coding Guidelines）

本规范解决 AI 编程中反复出现的十类问题：重复造轮子、代码不复用、脏提交、文件乱放、测试滥用、大任务失控、移植失控、重构失控、架构偏移、配置漂移。

核心原则：**规范的执行不靠自觉，靠配置。** 每条规则都要有对应的机器约束（CLAUDE.md / .gitignore / hook / CI），让 AI 想违反都难。

## 1. 库的使用：禁止重复造轮子

AI 遇到数据库就手写 SQL，遇到多语言就用条件渲染硬编码，明明有成熟库非要自己实现一套。

- 每个项目维护技术选型清单 `docs/TECH_STACK.md`，列出"常见能力 → 指定方案"。动手前必须先查。
- 以下能力禁止自研，必须使用清单指定的库：

| 能力 | 禁止的做法 | 必须使用（按语言选） |
|---|---|---|
| 数据库访问 | 手拼 SQL 字符串 | ORM：SQLAlchemy / Prisma / GORM / TypeORM / Django ORM |
| 国际化 i18n | 条件渲染硬编码语言 | i18next / react-intl / vue-i18n / gettext |
| 日期时间 | 手写格式化/时区换算 | dayjs / date-fns / Arrow |
| 表单校验 | 手写校验散落各处 | zod / pydantic / json-schema |
| 认证 | 自造 token/加密逻辑 | 成熟方案：JWT 库 / OAuth 库 / 框架内置 |
| 分页/重试/缓存 | 手写循环 | 库或框架内置实现 |

- 选型阶梯（新增依赖前按此顺序检查，并说明走到了哪一级）：①标准库 → ②已安装依赖 → ③框架原生特性 → ④都不行才允许新增依赖，且 PR 说明理由并登记 `docs/TECH_STACK.md`。
- 自研仅剩两种合法场景：a) 现有库确实不满足需求（PR 中给出调研结论）；b) 包装层薄适配（如统一错误码的 ORM 封装）。

## 2. 代码复用：写之前先找

之前写过的功能，后续开发 AI 又重新实现一套。

- 接到任务的**第一步是搜索代码库**：grep 相似函数名、组件名、关键词，确认是否已有实现。
- 判定标准：已有实现完全满足 → 直接调用禁止重写；接近但不完全满足 → 扩展原实现而不是新建平行版本；确实没有 → 新写，公共逻辑放统一位置。
- 公共代码位置：工具函数 → `utils/`；UI 组件 → `components/`；服务/领域逻辑 → `services/`。禁止在业务目录新建 helper.py、util.js 私有副本。
- 重复代码红线：同一段逻辑（≥10 行或含分支/循环）出现第二份拷贝，必须提取到公共位置。

## 3. Git 提交：禁止提交非必要内容

AI 会把 sqlite 文件、日志、构建产物等提交进仓库。

- 统一 `.gitignore` 模板，至少覆盖：数据与本地状态（`*.sqlite` `*.db` `data/` 模型文件）、环境与密钥（`.env*` `node_modules/` `.venv/`）、构建产物（`dist/` `__pycache__/` `*.pyc`）、日志临时（`*.log` `tmp/` `.DS_Store`）、AI 工具本地状态（`.claude/settings.local.json`）。
- AI 提交纪律：
  - **构建不过不提交**：提交前必须通过构建/编译 + lint；本地构建环境跑不起来必须明确说明，由人决定。
  - **禁止 `git add .` / `git add -A`**，逐文件添加，提交前 `git diff --staged` 审查。
  - 一个 commit 只做一件事；格式化、重构、新功能不混提交。
- 机器约束：CI 第一道门禁 build + lint；pre-commit 拦截大文件（1MB）与二进制/数据库后缀；diff 出现 `.db` `.sqlite` `.env` `node_modules/` 直接失败。

## 4. 文档与测试：位置统一标准

| 内容类型 | 固定位置 |
|---|---|
| 单元测试 | `tests/`（镜像源码结构），或按语言惯例与源文件同目录——每项目选定一种后固定 |
| 集成 / E2E 测试 | `tests/integration/`、`tests/e2e/` |
| 测试数据 / fixture | `tests/fixtures/` |
| API 文档 | `docs/api/` |
| 设计文档 / spec | `docs/design/` |
| 技术选型清单 | `docs/TECH_STACK.md` |
| 一次性报告 / 调研笔记 | `docs/notes/`，超 30 天未引用可清理 |
| 运维 / 部署文档 | `docs/ops/` |

- 命名：测试文件 `test_<模块名>.<ext>`（或语言惯例），文档用 kebab-case 英文文件名 + 中文正文。
- 禁止：仓库根目录散落 `*.md` 报告；生成 `README_新.md`、`说明(2).md` 平行副本。

## 5. 测试执行：禁止长而无用的测试

- **相关性质则**：只跑与改动相关的测试。改了 module_a → 只跑 module_a 的单测 + 依赖它的模块测试 + lint。全量回归只在发版前和 CI nightly 执行。
- 执行测试前必须说明："本次改动涉及 X，将运行 Y 测试（预计 Z 秒）"。单次 >3 分钟需先确认。
- 超时上限：单用例 60s；本地验证一轮 ≤5 分钟。不得编写依赖真实外部服务、真实大数据集、sleep 模拟时间的测试；一律 mock / fixture / fake。
- 想确认逻辑正确时优先写**最小检查**（一个断言、一次 dry-run），不搭完整测试脚手架。临时验证脚本放 `tmp/`（已 gitignore），不留仓库。

## 6. 大型任务：禁止 AI 造火箭

把工程量过大的任务直接丢给 AI（如"把单体改成 SaaS"），AI 产出巨型改造方案并大面积动手。

- 任务分级（就高不就低）：

| 级别 | 判定标准 | 流程 |
|---|---|---|
| 小 | ≤3 个文件，无接口/表结构变更 | 直接做 |
| 中 | 4–10 个文件，或改动公共模块 | 先列改动清单，确认后动手 |
| 大 | >10 个文件；表结构/数据迁移；API 破坏性变更；跨模块架构调整 | 强制走方案审批 |

- 大任务门禁：先产出《影响评估》放 `docs/design/`（目标、涉及模块清单、迁移方案、不兼容变更、回滚方式、分阶段计划），**人工审批后才写代码**。
- 一句话需求 → 先复述理解的范围 + 工程量估计，人确认后再进方案。
- **质疑义务**：接大任务必须先回答"是否有更小的实现路径？"。要"改成 SaaS" → 多数真实需求是加租户字段 + 行级过滤；要"换框架" → 先确认是否只缺某个库。给不出更小路径也要说明代价，让人决策。
- 大任务必须拆阶段：每阶段独立可验证、独立 PR、不破坏现有功能。重写/删除模块前必须有测试覆盖或回滚手段。

## 7. 代码移植：薄适配优先，公共资产库化

移植方式决策阶梯（从轻到重，**就低不就高**）：

| 级别 | 方式 | 适用条件 |
|---|---|---|
| 1 | 直接依赖 | 能直接引用（同 monorepo / 已发私有包）→ 不复制任何代码 |
| 2 | 抽库引入 | 基础能力被 ≥2 个项目使用 → 抽独立仓库，submodule 或私有包引入 |
| 3 | 薄适配移植 | 只此一处使用 → 原样复制 + 外层适配，原代码最小改动 |
| 4 | 重构移植 | 原代码与目标架构严重冲突，且影响评估中说明 2、3 级为何不可行，审批后才动 |

- **移植 = 搬运，不是重写**：diff 只允许三类——import/路径、项目基础设施接入（日志/配置/错误码）、PR 中逐条列出的必要修改。禁止顺手重构、加抽象层、"顺手优化"。
- 入库时标注来源（`来源: a-project@a1b2c3d`），后续才能 diff 同步上游修复。
- 同一段代码被第二个项目需要 → **立即抽库**，禁止第二份拷贝。库要求：独立仓库、自带 README 和测试、打 semver tag。
- submodule 纪律：改动一律在上游提交发版，宿主只更新版本指针（显式 commit，不混进其他提交）。

## 8. 重构：只做必要的，禁止反复横跳

- **重构与功能分离**：功能 PR 禁止夹带重构。判定："这个改动删掉，本次功能还成立吗？"成立 → 是重构，挪独立 PR。唯一例外：接入本次功能必须的最小结构调整，且 PR 逐条说明。
- 重构合法性门槛（必须命中其一）：挡住了本次需求；重复代码出现第二份；同一处反复出 bug。**"更优雅"不是理由**；说不清场景的性能/可维护性优化不算。
- **禁止反复横跳**：
  - 设计决策落盘：`docs/design/adr/` 维护轻量决策记录（背景、选定方案、否掉的方案及原因）。已决策事项 AI 不得重新发明；接手任务先读相关 ADR。
  - 30 天内同一段代码被重构两次以上 → 震荡，停止改动，先补 ADR 由人拍板。
  - "改回来"式提交必须引用当初 ADR 并说明结论为何失效。
  - 一个标识符 30 天内只允许改名一次。
- AI 执行纪律：功能任务中发现坏味道 → 不动手，在交付说明列"发现但未改"清单。任务没要求时不做任何超范围的重命名、移动、格式重组。

## 9. 架构一致性：定了的架构必须遵守

架构决策存在于会议里，没传达给后续 AI 会话，AI 按通用习惯另起炉灶（如 HTTP 直连替代 P2P），本地测试正常，部署后不可用。

- 架构约束两处落盘：为什么 → ADR；**必须/禁止 → 直接写进 CLAUDE.md 的"架构红线"节**（AI 稳定读取的只有 CLAUDE.md）。格式示例：

  ```markdown
  ## 架构红线（违反即打回）
  - 前后端所有通信走 P2P 通道（<库名>）。禁止新增 HTTP/WebSocket 直连端点，禁止新监听端口。
  - 数据访问只走 ORM + <指定库>。禁止直连其他服务的数据库。
  - 所有出站外部请求必须经 <网关/代理>。
  ```

- **自查义务**：新增/修改涉及通信、端口、存储、认证、外部服务的代码时，必须在交付说明中显式声明："本次新增了 X（端点/端口/连接/存储），对照架构红线检查结果为 Y"。对架构而言没有小事。
- 环境差异验证：涉及网络拓扑的功能，localhost 单进程跑通**不算验证**；部署后自动跑关键路径冒烟测试。
- 约束变更走流程：新通信通道、新存储、新端口 = 架构变更，先补 ADR 评审，禁止在功能 PR 里形成既成事实。
- 机器约束：CI 静态扫描红线模式（`fetch(` `axios` `http://` `listen(` 新端口等），命中打回。

## 10. 环境配置：单一格式，单一来源

- 一个项目只允许一种配置格式（yaml / toml / json / env 四选一），在 CLAUDE.md 中声明。禁止混用；框架强制的文件除外。AI 不得为"更方便"引入第二种格式。
- 配置结构单一来源：基础配置（如 `config/default.yaml`）承载全部配置项 + 默认值（不做额外配置也能启动）；环境文件只放差异覆盖项，**禁止各环境维护全量副本**。新增配置项只加在基础配置一处。
- 环境变量与脱敏只用于密钥（密码 / token / key），且必须登记 `.env.example`。非密钥（地址、超时、开关、阈值）直接写值入库——配置结构本身不是秘密。
- **AI 禁止擅自把明文值改成环境变量引用**：这是部署行为变更，必须人工确认部署侧已配好才能合入。脱敏只作用于集中定义的密钥清单；排障/临时日志不打码。
- 配置改动必须随功能 PR 一起提交，并在交付说明中列出改动清单。改了不提交 = 功能未完成。
- 机器约束：启动时 schema 校验（pydantic-settings / zod），缺项第一秒报出；CI 对拍环境覆盖文件键 ⊆ 基础配置键集。

## 落地机制总览

| 规则 | 人看的文档 | 机器约束 |
|---|---|---|
| 1 用库 | 本文档 + TECH_STACK.md | CLAUDE.md 指令 + review 抽查 |
| 2 复用 | 本文档 | CLAUDE.md 指令（先 grep 再写）+ 重复码检测 |
| 3 提交 | 本文档 | 统一 .gitignore + pre-commit + CI 拦截 |
| 4 文档测试位置 | 本文档 + 项目 CLAUDE.md 目录表 | CI 路径检查 |
| 5 测试执行 | 本文档 | CI 分层 + 超时配置 |
| 6 大任务控制 | 本文档 | 方案门禁 + PR 尺寸卡点 + 停手指令 |
| 7 移植控制 | 本文档 + 库仓库 | 决策阶梯 + 来源 diff review |
| 8 重构控制 | 本文档 + ADR 目录 | 功能/重构分离 + 触发条件 + churn 巡检 |
| 9 架构一致性 | 本文档 + CLAUDE.md 架构红线 | 静态扫描 + 部署冒烟 |
| 10 环境配置 | 本文档 + CLAUDE.md 格式声明 | 单一格式 + schema 校验 + CI 键对拍 |

新项目 checklist：复制统一 .gitignore → 从模板初始化 CLAUDE.md → 装 pre-commit hooks → 建 docs/、tests/ 骨架 → 接入 CI。

可直接复制到各项目 CLAUDE.md 的规则片段见 [references/claude-md-snippets.md](references/claude-md-snippets.md)。
